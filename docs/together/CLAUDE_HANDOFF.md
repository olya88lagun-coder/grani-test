### Коммерческие решения
Один тариф 599 ₽/30 дней за двоих пока гипотеза. Нет годовой предоплаты/заморозки. Оплату не предлагать до вступления обоих.

Идемпотентная выдача интервалов; ранний платёж не прибавляет уже предоставленные дни. unpaid gaps и overlapping intervals не считать дважды.
Пауза напоминаний не останавливает оплаченный срок. Выход одного закрывает совместную программу и будущие списания; политика остатка/возврата требует фиксации до денег.
При обычной отмене продления заработанные книги остаются; при выходе/отзыве источников новые скачивания ограничиваются согласно EDGE_CASES.

**Правила.** Живая оплата включается флагом и не включается публично до этапов 1–2: до тех пор платежи только на тестовом шлюзе. Контент месяцев 4–12 готовится параллельно и не блокирует код. Автосписание и возвраты по webhook отложены до данных пилота и решения владельца по остатку срока при выходе. После каждого этапа сюда добавляется запись: коммит, сделано, проверено, ограничения, следующая задача; раздельно сообщаются «код подготовлен», «проверки выполнены», «PR создан», «слияние/деплой выполнены».

**Статус этапа 0.** Код подготовлен в `feat/together-backend` (коммиты `054e2ad`…`d96dc95` плюс сквозной тест и документы). Контракт для экранов (этап 1, Codex):
`POST /api/together/spaces` → `{ ok, spaceId, inviteUrl }` (ссылка `/together/invite/<token>`, токен показывается один раз);
`POST /api/together/invite` (перевыпуск) → `{ ok, inviteUrl }`; `GET /api/together/invite/[token]` → `{ ok, valid }` (без входа);
`POST /api/together/invite/request` `{ token }`; `POST /api/together/invite/confirm` `{ accept: boolean }`;
`POST /api/together/leave` `{ acknowledged: true }` → `{ ok: true }`; `GET /api/together/space` → `{ ok, space | null }`
(`status`, `myRole`, `members[]`, `pendingRequest`, `access: { active, accessUntil, stage, canRenew }`);
`POST /api/together/purchases` `{ email }` → `{ ok, url, purchaseId }` (409 `not_available`: пространство не готово или уже оплачено больше 30 суток вперёд; 409 `busy`: платёж ещё создаётся, повторить через секунду); `GET /api/together/purchases/[id]` → `{ ok, id, status, granted }`.
Владелице: `GET /api/admin/together` → `{ paidWithoutAccess[], closedWithRemaining[] }`.
Коды ошибок: 400 неверный ввод или нет подтверждения, 401 нет входа, 403 чужой origin, 404 не найдено или нейтральный отказ, 409 конфликт состояния, 429 лимит, 502 шлюз, 503 оплата не настроена.
Возврат с оплаты ведёт на `/together?purchase=<id>`; страницы `/together` и `/together/invite/[token]` делает этап 1.
Правило потолка: покупать можно, пока оплаченного доступа осталось не больше 30 суток (сразу после первой оплаты второй платёж допустим, третий нет).

### Вход в раздел: витрина для всех без пространства — Claude · 2026-10-07
Раньше красивую витрину видел только не вошедший человек; вошедший без пространства сразу попадал на экран создания («Подтвердите возраст») и мог уйти. Теперь:
- `/together`: не вошёл → витрина; вошёл, но пространства нет (и нет возврата с оплаты) → витрина; есть пространство (ожидание, подтверждение или активное) → экран пространства.
- Кнопка витрины ведёт: не вошедшего во вход с возвратом на `/together/start` (`togetherReturnPath("space")` теперь `/together/start`), вошедшего без пространства сразу на `/together/start`, пару с пространством в `/together` («Открыть моё пространство»).
- `/together/start`: экран создания (согласие 18+ и кнопка). Не вошёл → вход; пространство уже есть → `/together`; закрытый пилот и выключенная функция работают как на `/together`. Код `from` сохраняется (параметр и cookie).
- `/together/about`: витрина всегда, в том числе паре с пространством (ссылку можно показать друзьям); не индексируется; на экране пространства есть тихая ссылка «Как «Вдвоём» выглядит для тех, кто видит его впервые».
- После выхода из пространства другой участник при обновлении страницы видит витрину, а не форму создания.
**Проверено:** e2e `together-ui` (9 сценариев), `together-cards-ui` (2) на реальном сервере и `together-pilot` в режиме pilot; тесты логики возврата после входа.

## Чеки «Мой налог»: напоминание и удобная страница — Claude · 2026-10-07
**Что выяснилось.** Встроенная отправка чеков для самозанятых в ЮKassa закрыта с 29 декабря 2025 года (ответ поддержки): платежи идут штатно, но чек в налоговую не передаётся, регистрировать доход нужно вручную в «Мой налог». Официального открытого API для обычных самозанятых нет. Автоматизацию через неофициальный кабинет `lknpd.nalog.ru` и переход на другого эквайера (Robokassa «Робочеки СМЗ») решили отложить: сейчас вариант с ручным оформлением, но с напоминанием и удобной страницей. Вернуться к автоматике стоит, когда оплат станет больше примерно десяти в день.
**Напоминание в ВК.** При каждой оплаченной покупке (кроме бесплатных у владелицы) сайт ставит задачу `receipts_pending` ([queues.ts](../../packages/core/src/queues.ts)): одна на окно в 10 минут (ключ — номер окна), отложенная до конца окна, чтобы в сообщение попали и оплаты, пришедшие позже первой. Воркер при отправке считает чеки к отправке и шлёт владелице одно сообщение «Чеков к отправке: N на X ₽. Открыть: …/admin/receipts» (без имён, почты и номеров платежей); при нуле чеков молчит. Сбой напоминания оплату не ломает (в журнал пишется ошибка). Нужно, чтобы работало в production: (1) в `.env` задан `OWNER_IDENTITY=vk:<id>` и этот аккаунт хотя бы раз входил на сайт; (2) владелица разрешила сообщения от сообщества ВК (кнопка «Разрешить сообщения» на сайте), иначе доставка пропускается; (3) `VK_GROUP_TOKEN` задан у воркера.
**Страница `/admin/receipts`.** Итог вверху («К отправке: N чеков на X ₽»), у каждого чека «оплачено сегодня» или «ждёт N дней» (после 5 дней выделено; это мягкая подсказка, не юридический срок), кнопки копирования названия услуги, суммы (рубли без знака) и почты, три шага по оформлению. «Чек отправлен» работает как раньше и стирает почту.
**Проверено:** типы чистые, 912 юнит-тестов; e2e `purchase.spec.ts` новый сценарий страницы чеков (счётчик, «оплачено сегодня», копирование трёх строк в буфер, «Чек отправлен») на реальном сервере. Не проверено вживую: доставка сообщения в ВК и сама отсрочка задачи на реальной очереди (локальная БД PGlite с несколькими подключениями нестабильна); `startAfter` числом задаёт секунды, повтор с тем же `id` игнорируется (проверено по коду pg-boss).

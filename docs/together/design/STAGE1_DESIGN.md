## Цель и границы
Пара без обязательного теста понимает, как создать общее пространство, вступить по приглашению, проверить личность второго участника и оплатить один 30-суточный доступ за двоих.
Макеты продолжают утверждённый стиль «Глина». Контракт сервера не меняется. Работа затрагивает только docs/together, не приложение, БД или шлюз.
Шесть новых форматов, вопросы/ответы и книга уже описаны отдельными материалами; сейчас оформляется вход к ним.
Живую оплату не включать публично до готовности этапов 1–2 и решения владельца. Макет не является разрешением на публикацию.
Три бесплатных вводных вопроса остаются в концепции. Их прохождение/учёт ещё не реализованы серверным этапом 0: нельзя считать ready-space доказательством завершения знакомства.

## Визуальная система
Cormorant Garamond 300 и Golos Text 400/600 из существующих assets/fonts.
Цвета: бумага #FFFCFA, глина #F6E8E1/#EED8CF, сливовый акцент #4A2230; существующие цвета текста/ошибок.
Desktop: основной смысл слева, действие или состояние на глиняной поверхности справа. Mobile: сначала объяснение, затем действие; всё в одной колонке.
Парный знак — две пересекающиеся линии, не замена логотипа.
Кнопки минимум 44px, текстовые статусы, понятные подписи, focus-visible и reduced-motion.
Для ошибок нет оценки отношений или обвинения партнёра. Длинные отображаемые имена выводятся как текст и переносятся.
Верхняя review-полоса и нижние роли/состояния — только инструменты просмотра.

## Маршруты и очередность
- /together: публичное предложение при отсутствии входа; после входа состояние своей пары.
- /login?returnTo=<разрешённый локальный путь>: существующий вход с контекстом Вдвоём.
- /together/invite/[token]: публично только валидность; без имён пары.
- Возврат провайдера: /together?purchase=<id>. Эта строка не доказывает оплату.
Макет переключает экраны через ?view=... только для review; production таких query-presets не имеет.

## Согласие и вход
Существующий LoginPanel сначала фиксирует согласие POST /api/consent. Лишь после успеха показывает VK ID/Telegram; Telegram зависит от фактической настройки.
В текстах для together-контекста: «Войдите в свой аккаунт» и «После входа вернём вас к приглашению/созданию пары».
Старый сценарий hasPendingResult и перенос результата теста не удалять и не перенаправлять по умолчанию во Вдвоём.
returnTo — отдельная техническая задача Claude. Разрешать только заранее определённые локальные маршруты /together и /together/invite/<token>, плюс валидный возврат покупки.
Не принимать произвольный внешний URL, protocol-relative //host, javascript:, пути со сменой origin или свободные редиректы. Проверку выполнить и на входе, и перед окончательным redirect.
После полного VK/Telegram callback возвращать нужный контекст; без together returnTo прежний поток работает как раньше.
Присоединение не равно разрешению на сообщения сообщества/бота.

## Создание и приглашение
GET /api/together/space сначала определяет, есть ли своё пространство. Не создавать второе автоматически.
POST /api/together/spaces выдаёт { ok, spaceId, inviteUrl }. Сырой токен показывается один раз.
Readonly-поле имеет label; copy показывает успех только после Clipboard API success, иначе выделяет ссылку с честным предложением ручного копирования.
После обновления страницы GET space не возвращает inviteUrl. Не восстанавливать токен из журналов или БД; экран lost предлагает перевыпуск.
POST /api/together/invite отзывает старое приглашение. Перед вызовом показать последствия; после успеха сохранить новый URL только для отображения/копирования в текущем контексте.
Период 7 суток брать из TOGETHER_INVITE_TTL_DAYS. Не придумывать точное время истечения: endpoint не возвращает expiresAt.
До запроса/подтверждения участников кнопку покупки не показывать.

## Присоединение и подтверждение
GET /api/together/invite/[token] возвращает только { ok, valid }. До входа не показывать имена, состав пары, историю или цену ранее оплаченного доступа.
POST /api/together/invite/request { token } возвращает requested. По ссылке второй участник лишь просит вступить.
Ожидание не обещает ещё не реализованные уведомления.
GET /api/together/space может оставаться null у запросившего до подтверждения: это не повод автоматически создать ему вторую пару.
Для ожидания допустим ограниченный опрос GET space. После обновления страницы продолжение по ссылке через явную кнопку повторяет идемпотентный request; отдельного GET pending-state у партнёра сейчас нет.
Инициатор получает pendingRequest.displayName только в своём GET space и подтверждает POST /api/together/invite/confirm { accept: true } либо отклоняет { accept: false }.
После подтверждения заново прочитать GET space, не полагаться на оптимистическую подпись «пара готова».
Отказ возвращает инвайт в open, не закрывает пространство. Если сырого URL в текущем контексте уже нет — lost/reissue.
Ошибки own_invite/already_in_space/requester_unavailable не раскрывают чужую пару. Вошедшему человеку можно предложить открыть собственное существующее пространство.
Если valid=false, причины истечения/отзыва/использования не различать публично.

## Оплата и продление
Цена/длительность берутся из TOGETHER_PRICE_KOPECKS и TOGETHER_PERIOD_DAYS. В макете показан проверенный текущий пример 599 ₽ / 30 дней, не новый тариф.
Условия на экране: «Одна оплата за двоих», «Автоматических списаний нет», почта для чека, существующая /offer и /privacy. Ссылки не заменяют юридические страницы.
GET space должен показывать active-пространство с двумя участниками и допустимость покупки. canRenew определяет доступность продления.
POST /api/together/purchases { email } возвращает { ok, url, purchaseId }. До ответа кнопку блокировать, двойной click не создаёт новую локальную попытку.
confirmationUrl открывается через предусмотренный redirect на провайдера; не строить фальшивую форму реквизитов на сайте.
purchaseId используется для статуса GET /api/together/purchases/[id]. Не обращаться к старому отчётному GET /api/purchases/[id].
401: повторный вход с безопасным возвращением к текущей задаче; 409 busy: повтор того же старта после секунды, с ограничением попыток; 409 not_available: перечитать space и показать готовность пары/потолок; 503: оплата отключена, не показывать ложный успех.
Существующий сервер повторно возвращает открытый платёж пространства вместо второго — UI сохраняет/уточняет созданную покупку, не создаёт цикл новых оплат.

После возвращения:
1. Прочитать статус покупки.
2. pending: «Проверяем оплату».
3. succeeded без granted: «Платёж подтверждён. Доступ проверяем», без кнопки повторной оплаты.
4. succeeded + granted: дополнительно перечитать GET space. Успех программы показывается только при текущем active space и access.active.
5. Если пространство закрыто/доступ не действует, не обещать открытие программы по одному историческому granted. Показать состояние проверки/закрытия; владелец видит paidWithoutAccess/closedWithRemaining.
6. cancelled: проверенный статус, возможность вернуться к условиям; повторный платёж не запускается автоматически.

Предложение для polling: GET раз в 5 секунд, максимум 12 попыток на одном экране; затем ручная проверка. Вкладка скрыта — опрос на паузе. Ошибка соединения сохраняет purchaseId и возвращает возможность безопасного повтора.
Статус актуализируется при возвращении вкладки, без бесконечного polling в фоне.
Сразу после первой оплаты второй период может быть доступен; при остатке больше 30 суток третья покупка закрыта. Правило сервера не заменять календарным «месяцем».
accessUntil форматировать в часовом поясе пользователя с датой и временем. Ранний платёж добавляет период после текущего; не выдаёт награды вперёд.
Данные карты/реквизиты не выводить второму участнику; статус доступа и покупки может быть доступен обоим согласно API.

## Выход
Активное пространство содержит спокойную ссылку выхода. Dialog объясняет прекращение общей программы/доступа для обоих и отсутствие автоматического возврата/переноса остатка.
Кнопка disabled до отдельного acknowledgment checkbox. POST /api/together/leave { acknowledged: true } только после явного действия.
Escape/отмена возвращает фокус и не выполняет выход. После успеха перечитать состояние и очистить совместные данные в клиенте.
Политика остатка срока требует решения владельца; макет не обещает возврат и не меняет сервер.

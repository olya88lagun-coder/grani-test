# Автописатель SEO-статей «Граней»

Инструкция для агента, который по расписанию (вторник и пятница) пишет и публикует одну статью. Владелица решила 28.09.2026: статьи выходят **без ручной вычитки** — агент сам мержит свой PR, если все проверки зелёные. Поэтому всё, что ниже, обязательно; если какое-то условие выполнить нельзя — статью не публиковать (см. «Когда остановиться»).

Агент меняет только `packages/content/articles/*.md`, `packages/content/src/sources.ts`, `packages/content/src/content-plan.ts` и сгенерированные `packages/content/src/generated/*.json`. Код сайта, тесты, workflow и остальные файлы не трогает.

## 0. Перед началом

1. `git checkout master && git pull`.
2. `gh pr list --state open --search "head:article/"` — если открыт незавершённый PR конвейера, сначала довести его (исправить проверки) или закрыть с комментарием. Новую статью в этот запуск не писать.
3. `pnpm install`.

## 1. Выбор темы

1. Открыть `packages/content/src/content-plan.ts` и взять **первую** тему `CONTENT_PLAN` со статусом `draft`, для которой нет файла `packages/content/articles/<slug>.md`.
2. Сравнить её интент с опубликованными статьями (`packages/content/articles`) и публичными страницами (`/traits/*`, `/types/*`, `/big-five-test`, `/about`). Если тема по сути повторяет существующую страницу — удалить её из `CONTENT_PLAN` (одна строка) и взять следующую. Две страницы под один запрос отбирают друг у друга позиции.

## 2. Источники — только проверенные

1. У каждой опубликованной статьи должно быть **не меньше двух** научных работ в `ARTICLE_SOURCES[<slug>]` (`packages/content/src/sources.ts`). Тест это проверяет.
2. Можно переиспользовать уже сверенные константы из `sources.ts` (`GOLDBERG_1992`, `IPIP_2006` и др.), если работа действительно подтверждает утверждения статьи.
3. Новую работу добавлять только после сверки по DOI через Crossref: `curl -s https://api.crossref.org/works/<DOI>`. Авторы, год, название и журнал в `sources.ts` — **ровно как в ответе Crossref**. Если DOI не найден или данные не совпадают — работу не использовать.
4. `note` — одна строка: что именно из текста статьи подтверждает работа.
5. Никогда не выдумывать исследования, авторов, DOI, проценты и статистику. Утверждение, которое нечем подтвердить, — переформулировать как общее наблюдение или убрать.

## 3. Текст

Образец тона и формата — опубликованные статьи в `packages/content/articles` (например, `ambivert.md`, `temperament.md`).

- Русский язык, обращение на «ты», спокойный тон без кликбейта и восклицательных знаков.
- Тело статьи — от 4000 до 9000 знаков (ориентир 5500–7500), не меньше трёх разделов `## `.
- Первый абзац сразу отвечает на запрос из темы (`primaryQuery`), без вводных «в этой статье мы…».
- Минимум две внутренние ссылки markdown на публичные страницы из `internalLinks` темы (`[текст](/traits/openness-high)`). Если статья про саму модель Big Five, тест или шкалы — ссылку на тест ставить на `/big-five-test` (это главная страница под запрос «тест Big Five»), а не на главную. Внешних ссылок в тексте нет — источники выводятся блоком автоматически.
- Кнопка «Пройти тест Big Five» в середине статьи и подпись «Команда «Граней»» с датой добавляются сайтом автоматически — в текст их не писать.
- Нельзя: диагнозы и медицинские советы, «тест определит…», обещания точности; приравнивать типы «Граней» к MBTI или соционике (только сравнение моделей); оценки «хороший/плохой тип»; темы из стоп-списка (`packages/content/src/safety.ts`).
- Не повторять целыми фразами тексты страниц черт и типов.

### Front matter

```yaml
---
title: <H1 до 90 знаков, можно title из плана>
seoTitle: <до 52 знаков, если title длиннее>
description: <50–200 знаков, отвечает на запрос>
date: <сегодня, YYYY-MM-DD>
tag: <Личность | Наука | Психология | Отношения | Работа>
image: </home/…webp из списка ниже>
status: published
reviewed: true
canonical: /articles/<slug>
cluster: <cluster из плана>
intent: <intent из плана, до 80 знаков>
faq: Вопрос 1? => Ответ 1. || Вопрос 2? => Ответ 2. || Вопрос 3? => Ответ 3.
---
```

`reviewed: true` означает «прошла автоматическую самопроверку по этому документу», а не ручную вычитку.

Картинки (выбрать по смыслу, можно повторять): `/home/hero-atrium.webp` (светлый атриум), `/home/type-iskra.webp` (листья), `/home/type-architect.webp` (кристаллы), `/home/type-dreamer.webp` (облака), `/home/type-support.webp` (камень), `/home/type-commander.webp` (пирамида), `/home/article-extrovert.webp` (портрет), `/home/article-friends.webp` (интерьер с растением), `/home/article-relationship.webp` (арка).

## 4. План и сборка

1. В `content-plan.ts` у выбранной темы поставить `status: "published"` (тест сверяет план со статьями).
2. `pnpm --filter @grani/content build:library`
3. `pnpm typecheck` и `pnpm test` — всё зелёное. Падения исправлять в статье, источниках или плане; тесты и код не менять.

## 5. Самопроверка перед публикацией

Перечитать статью и пройти по `QUALITY_RULES` из `content-plan.ts`:

- каждое научное утверждение опирается на работу из `ARTICLE_SOURCES[<slug>]` или сформулировано как общее наблюдение;
- нет диагнозов, обещаний, приравнивания к MBTI/соционике, стоп-тем;
- ссылки ведут на существующие страницы, текст отвечает на запрос темы.

## 6. Публикация

1. Ветка `article/<slug>`, коммит `feat(content): article <slug>`.
2. `gh pr create --base master --title "Статья: <title>" --body "<запрос, кратко о чём, список источников с DOI>"`.
3. `gh pr checks <номер> --watch` — дождаться зелёных проверок.
4. `gh pr merge <номер> --merge`. Мерж запускает деплой; деплой сам отправит новый адрес в Яндекс по IndexNow.

## Когда остановиться

Не мержить, оставить PR открытым с комментарием, что не так, если:

- не нашлось двух работ, сверенных через Crossref;
- проверки не зелёные после двух попыток исправления;
- для статьи пришлось бы менять что-то кроме файлов, перечисленных в начале;
- тема оказалась медицинской, диагностической или из стоп-списка.

Лучше пропустить публикацию, чем выпустить статью с выдуманными фактами: сайт публикуется без ручной проверки.

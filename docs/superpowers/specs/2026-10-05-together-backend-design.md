# «Вдвоём»: серверный слой пространства и оплаты — спецификация

Дата: 2026-10-05. Ветка: `feat/together-backend` (от `feat/together-prototype`, стопка поверх PR #37).
Продолжает `docs/together/ARCHITECTURE.md`, `SPEC.md`, `PRICING.md`, `EDGE_CASES.md`, `CLAUDE_HANDOFF.md`.

## Разделение ответственности
- **Claude Code:** вся техническая часть: БД, миграции, сервисы, API, оплата, безопасность, тесты, CI.
- **Codex:** визуал и экраны (палитра «Глина», `docs/together/design/*`), тексты интерфейса.
- Контракт между ними: HTTP-маршруты и формы ответов из раздела «API» ниже. Экраны подключаются к ним без знания схемы БД. Изменение контракта оформляется записью в `CLAUDE_HANDOFF.md`.

## Цель
Рабочий и проверяемый серверный фундамент «Вдвоём»: два аккаунта образуют общее пространство и оплачивают общий доступ на 30 суток. Деньги принимаются безопасно: повтор webhook, гонки и закрытие пространства не создают лишний доступ и не теряют платёж.

Критерии успеха:
1. Два независимых пользователя без результатов теста создают пространство, приглашают и принимают друг друга.
2. Третий человек и второй активный кабинет у одного человека невозможны на уровне БД.
3. Один подтверждённый платёж даёт ровно один 30-суточный период ровно один раз, при любых повторах и гонках.
4. Срок доступа и «предоставленное время» считаются чистыми функциями, покрытыми граничными тестами.
5. Старые покупки отчётов, пары и результаты работают без изменений.
6. Платёж без возможности выдать доступ не теряется молча.

## Не входит в эту спецификацию
Экраны и `returnTo` после входа (Codex/следующий этап), вопросы и ответы с раскрытием, каталог, книга, награды, уведомления, автосписание, возвраты по webhook, смена плательщика с переносом карты, годовой тариф.

## Решения владельца, нужные до живых денег (не блокируют разработку)
- Политика остатка оплаченного срока при выходе участника: пока ничего не возвращается и не переносится автоматически, такие случаи попадают в список на ручное решение.
- Автоматизация чеков «Мой налог»: сейчас вручную по общей странице чеков.
- Окончательная цена: 599 ₽ / 30 суток — рабочая гипотеза, лежит в одной конфигурации.

## Модель данных

### Новые таблицы (`packages/db/src/schema.ts`)
Имена с префиксом `together_`. Все инварианты обеспечивает БД, а не только код.

**`together_spaces`**: `id uuid pk`, `status` enum (`pending` | `active` | `closed`), `created_at`, `closed_at null`, `closed_by uuid null` (fk users, set null), `closed_reason null` enum (`left` | `account_deleted`).
Пространство `pending`, пока в нём один человек; `active`, когда двое; `closed` необратимо.

**`together_members`**: `id`, `space_id` fk cascade, `user_id` fk users, `role` enum (`initiator` | `partner`), `joined_at`, `left_at null`.
- unique `(space_id, role)`: физически не более двух участников и по одному на роль;
- unique `(space_id, user_id)`;
- частичный unique `(user_id)` where `left_at is null`: один активный кабинет на человека.

**`together_invites`**: `id`, `space_id` fk cascade, `token_hash text unique` (SHA-256 токена; сам токен не хранится), `inviter_id`, `status` enum (`open` | `requested` | `accepted` | `revoked`), `requester_user_id null`, `requested_at null`, `confirmed_at null`, `expires_at`, `created_at`.
- частичный unique `(space_id)` where `status in ('open','requested')`: один живой инвайт на пространство;
- «истёк» вычисляется по `expires_at`, отдельный статус не нужен.
- TTL приглашения: **7 суток** (конфигурация `TOGETHER_INVITE_TTL_DAYS`). `ARCHITECTURE.md` называет 48 часов, `EDGE_CASES.md` (поздний документ) 7 суток. Выбрано правило последнего, фиксируется в ADR-001.

**`together_access_periods`**: `id`, `space_id` fk cascade, `purchase_id uuid not null unique` fk purchases, `starts_at`, `ends_at`, `created_at`; check `ends_at > starts_at`.
Журнал оплаченных интервалов. Уникальный `purchase_id` делает выдачу идемпотентной.

### Изменения в `purchases`
- enum `product` + значение `together_30d`;
- колонка `space_id uuid null` fk `together_spaces` on delete set null (записи об оплатах переживают удаление, как `result_id`/`pair_id`);
- check `purchases_at_most_one_target` расширяется: `num_nonnulls(result_id, pair_id, space_id) <= 1`;
- индекс по `space_id`.
Миграция добавляется новым файлом drizzle; существующие миграции не редактируются.

### Чистая логика доступа (`packages/core/src/together-access.ts`, без БД)
- `TOGETHER_PERIOD_DAYS = 30`, `TOGETHER_PRICE_KOPECKS = 59900` — единственное место цены и срока.
- `nextPeriodStart(existing, paidAt)` = `max(paidAt, конец последнего периода)`, период длится 30 суток; пересечений нет, пропуск остаётся пропуском.
- `effectiveEnd(period, closedAt)` = `min(ends_at, closedAt)`: закрытие обрезает периоды.
- `providedPaidSeconds(periods, now, closedAt)` — сумма уже прошедших частей периодов без двойного счёта.
- `stage(seconds)` = `floor(seconds / (30·86400))`, не больше 12.
- `accessState(periods, now, closedAt)` → `{ active, accessUntil, remainingSeconds }`.
- `canRenew(periods, now)`: купить можно, только если оставшегося доступа меньше 30 суток (не более одного оплаченного периода вперёд; годовой предоплаты нет).
Все времена UTC.

## Поведение пространства (`apps/web/src/server/together-service.ts`)
Все операции — транзакции, строка пространства блокируется `FOR UPDATE`; индексы выше — вторая линия защиты.

1. **Создание.** Вошедший человек без активного кабинета создаёт пространство `pending`, становится `initiator`, получает приглашение. Сырой токен возвращается один раз (минимум 128 бит, как существующие токены). Перевыпуск отзывает прежнее приглашение.
2. **Просмотр ссылки (публично).** Только валидность. Для неверной, просроченной, отозванной или использованной ссылки один и тот же нейтральный ответ. Ни имён, ни данных пространства.
3. **Запрос вступления.** Вошедший по ссылке человек переводит приглашение в `requested`. Отказ, если это сам инициатор или у человека есть активный кабинет. Повтор тем же человеком идемпотентен; другой человек получает нейтральный отказ.
4. **Подтверждение (только инициатор).** Инициатор видит отображаемое имя запросившего (`auth_identities.display_name`) и подтверждает: в одной транзакции создаётся участник `partner`, пространство становится `active`, приглашение `accepted`. Отклонение возвращает приглашение в `open`, очищая запросившего.
5. **Выход.** Любой участник выходит без согласия партнёра. Требуется явный `acknowledged: true`. Пространство переходит в `closed`, `closed_at` ставится, живые приглашения отзываются, периоды перестают действовать (по `effectiveEnd`). Остаток срока автоматически не возвращается и не переносится.
6. **Удаление аккаунта.** `delete-user` закрывает активное пространство пользователя с причиной `account_deleted`; записи об оплатах сохраняются.

## Оплата (`apps/web/src/server/payments-service.ts` + `together-payments.ts`)
Основа — таблица `purchases` и существующий шлюз. Новый продукт не вызывает генерацию отчётов.

**`startTogetherPurchase`**
- Покупатель — любой из двух участников; пространство должно быть `active`; почта для чека обязательна (нормализация как сейчас).
- `canRenew` должен быть истинным, иначе `not_available`.
- Открытая оплата по пространству за последние 30 минут (от любого участника) возвращается повторно, вторая не создаётся.
- Описание для чека: «Доступ к «Грани. Вдвоём» на 30 дней для двоих». Сумма — `TOGETHER_PRICE_KOPECKS`.

**Выдача доступа**
- Статус меняет только `syncPayment` по ответу API шлюза (проверка суммы и номера покупки, как сейчас), return URL ничего не доказывает.
- После атомарного перехода `pending → succeeded` победивший в гонке вызывает `grantAccessPeriod(spaceId, purchaseId, paidAt)`: под блокировкой пространства считает `nextPeriodStart`, вставляет период с `ON CONFLICT (purchase_id) DO NOTHING`.
- Самовосстановление: при запросе статуса покупки и при повторном уведомлении `succeeded`-покупка без периода получает период.
- Если к моменту выдачи пространство `closed`, период не создаётся, покупка помечается условием «оплачено без доступа» и попадает в список владельца. Платёж не теряется молча.
- Диспетчеризация по продукту: отчёты — как сейчас, `together_30d` — выдача периода. Поведение старых продуктов не меняется.

**Владелец (`/api/owner/together`, читает `owner.ts`-проверку):** список (а) оплачено без доступа; (б) закрытые пространства с остатком оплаченного срока. Чеки подхватываются существующей страницей.

## API (контракт для Codex)
Все маршруты проверяют сессию на сервере, форма ошибок как в существующих `/api/*`.
- `POST /api/together/spaces` → `{ spaceId, inviteUrl }`
- `POST /api/together/invite` (перевыпуск) → `{ inviteUrl }`
- `GET /api/together/invite/[token]` → `{ valid: boolean }`
- `POST /api/together/invite/request` `{ token }` → `{ status }`
- `POST /api/together/invite/confirm` `{ accept: boolean }` → `{ status }`
- `POST /api/together/leave` `{ acknowledged: true }` → `{ status }`
- `GET /api/together/space` → `{ status, members[{ role, displayName }], access: { active, accessUntil, stage, canRenew } }` (чужие данные не отдаются)
- `POST /api/together/purchases` `{ email }` → `{ url }`
- Уведомление ЮKassa и `GET /api/purchases/[id]` используют существующие маршруты; для `together_30d` `reportUrl` ведёт на `/together`.
Перед написанием маршрутов читается документация установленного Next (`apps/web/AGENTS.md`).

## Безопасность
- Права определяются сессией и членством, а не токеном. Токен приглашения не даёт доступа к пространству.
- Токены приглашений хранятся хешем; в логах и аналитике токенов нет.
- Нейтральные ответы для чужих/просроченных ссылок; пространство не раскрывает личность пары.
- Rate limit на приглашение/запрос по существующему `rate-limit.ts`.
- Платёжные реквизиты видит только плательщик; статус доступа — оба участника.
- Ревью безопасности (`security-reviewer`) перед PR обязательно: аутентификация, пользовательский ввод, БД, платежи.

## Тестирование
Vitest с pglite (как сейчас), фейковый шлюз `payments/fake.ts`, покрытие ≥ 80%, `typecheck` и прежние тесты зелёные.
- Core: границы 30 суток, пропуск, пересечение, ранний платёж, обрезка при закрытии, `canRenew`.
- БД: третий участник, второй активный кабинет, повторный период на ту же покупку, check у `purchases`, регресс старых покупок отчётов.
- Сервис: чужое пространство (IDOR), гонка подтверждения, третий по ссылке, истёкшая/перевыпущенная ссылка, отказ инициатора, выход и удаление аккаунта.
- Оплата: повторный webhook, webhook не по порядку, ранний платёж, оплата после закрытия, сбой между `succeeded` и выдачей, неверная сумма.
- Параллельность: pglite однопоточный, поэтому гонки проверяются на уровне ограничений БД и порядка вызовов в транзакциях.
